# Описание таблиц базы данных

В проектируемой информационной системе база данных построена по принципу разделения доменных контекстов. Каждый основной сервис использует собственное PostgreSQL-хранилище, что позволяет снизить связанность компонентов, упростить сопровождение схемы и изолировать нагрузку между подсистемами учета активности, авторизации, управления пользователями, уведомлений, отчетности и управления endpoint-агентами.

В базе данных сервиса аутентификации используются таблицы `roles`, `auth_users` и `sessions`. Таблица `roles` хранит перечень ролей пользователей системы, например администратора, обычного пользователя, модератора и аудитора. Таблица `auth_users` предназначена для хранения учетных записей, используемых при входе в систему: логина, электронной почты, хеша пароля, признака активности и ссылки на роль. Таблица `sessions` содержит сведения о пользовательских сессиях и refresh-токенах, включая хеш токена, срок действия и связь с учетной записью.

В базе данных сервиса пользователей размещены таблицы `users` и `computers`. Таблица `users` описывает бизнес-профиль пользователя: идентификатор учетной записи, ФИО, подразделение и дату создания записи. Таблица `computers` хранит сведения о рабочей станции пользователя: имя хоста, версию операционной системы, IP-адрес, MAC-адрес, статус компьютера и время последней активности. Между таблицами `users` и `computers` задана связь один к одному, так как в рамках проекта за одним пользователем закрепляется одна рабочая станция.

В базе данных сервиса активности центральной таблицей является `activities`. Она хранит события компьютерной активности, поступающие от endpoint-агентов: идентификатор компьютера, пользователя и агента, дату и время события, тип активности, дополнительные сведения в формате JSON, URL, имя процесса, длительность действия, оценку риска и признак блокировки. Таблица `anomalies` предназначена для хранения выявленных отклонений, связанных с конкретными событиями активности. Таблица `activities_archive` используется для архивирования старых событий в рамках политики хранения данных. Таблица `activity_outbox` реализует паттерн transactional outbox и фиксирует события, которые должны быть опубликованы в RabbitMQ для дальнейшей обработки сервисами метрик, уведомлений и отчетов.

В базе данных сервиса управления агентами используются таблицы `agents`, `sync_batches`, `agent_policies`, `agent_policy_versions`, `agent_commands` и `agent_command_dlq`. Таблица `agents` хранит сведения об endpoint-агентах: связанный компьютер, версию, статус, время последнего heartbeat, состояние очереди, текущую версию политики и диагностическую информацию. Таблица `sync_batches` фиксирует пакеты синхронизации данных, переданные агентами. Таблица `agent_policies` содержит актуальные политики мониторинга, включая интервалы сбора, включенные коллекторы, порог риска, параметры блокировки, whitelist и blacklist. Таблица `agent_policy_versions` хранит историю изменений политик и позволяет отслеживать создание, обновление и откат конфигурации. Таблица `agent_commands` содержит команды, отправляемые агентам, их параметры, статус выполнения, количество попыток доставки и результат. Таблица `agent_command_dlq` используется для хранения команд, которые не удалось доставить или выполнить после заданного числа попыток.

В базе данных сервиса метрик используются таблицы `metrics`, `whitelists`, `blacklists`, `processed_event_inbox`, `activity_event_rollups` и `anomaly_event_rollups`. Таблица `metrics` хранит настраиваемые метрики и правила контроля активности. Таблица `whitelists` содержит разрешенные шаблоны, например домены, процессы или пути к файлам, а таблица `blacklists` хранит запрещенные шаблоны, по которым действия могут помечаться как рискованные или блокироваться. Таблица `processed_event_inbox` используется для идемпотентной обработки сообщений из RabbitMQ и предотвращает повторное применение одного и того же события. Таблица `activity_event_rollups` хранит агрегированные показатели активности по дате, компьютеру и типу активности. Таблица `anomaly_event_rollups` хранит агрегированные показатели аномалий по дате, компьютеру и типу отклонения.

В базе данных сервиса уведомлений используются таблицы `notifications`, `notification_templates`, `processed_event_inbox` и `notification_delivery_dlq`. Таблица `notifications` хранит уведомления для пользователей и администраторов: тип, заголовок, текст сообщения, канал доставки, адрес получателя, статус доставки, количество попыток и признак прочтения. Таблица `notification_templates` содержит шаблоны уведомлений, которые используются при формировании сообщений. Таблица `processed_event_inbox` фиксирует уже обработанные события и защищает сервис от повторной генерации одинаковых уведомлений. Таблица `notification_delivery_dlq` хранит уведомления, доставка которых завершилась ошибкой после исчерпания попыток.

В базе данных сервиса отчетов используются таблицы `daily_reports`, `user_stats`, `processed_event_inbox` и `report_daily_anomaly_rollups`. Таблица `daily_reports` содержит ежедневные агрегированные отчеты по рабочим станциям: дату отчета, идентификатор компьютера и пользователя, общее число событий, количество заблокированных действий, число аномалий и среднюю оценку риска. Таблица `user_stats` хранит статистику пользователя за период, включая общее активное время, список рискованных сайтов и количество нарушений. Таблица `processed_event_inbox` обеспечивает идемпотентную обработку событий при построении отчетных проекций. Таблица `report_daily_anomaly_rollups` хранит ежедневные агрегаты аномалий по компьютеру и типу отклонения.

В runtime-хранилище API Gateway используются таблицы `app_settings_documents`, `alert_rules`, `admin_audit_events` и `role_permissions`. Таблица `app_settings_documents` хранит настройки приложения в формате JSON. Таблица `alert_rules` содержит правила оповещения: контролируемую метрику, оператор сравнения, порог, окно анализа, уровень важности и настройки каналов уведомления. Таблица `admin_audit_events` используется для журнала аудита административных действий, включая исполнителя, действие, целевой объект, результат выполнения и время операции. Таблица `role_permissions` хранит соответствие ролей и разрешений, используемое для разграничения доступа к функциям системы.

Таким образом, структура базы данных отражает полный жизненный цикл обработки компьютерной активности: учет пользователей и рабочих станций, сбор событий endpoint-агентами, сохранение активности, выявление аномалий, публикацию событий через outbox, построение агрегатов, формирование уведомлений и отчетов, а также контроль действий администратора. Разделение таблиц по сервисам повышает устойчивость системы и соответствует микросервисной архитектуре проекта.
