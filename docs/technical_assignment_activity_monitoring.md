## 2. Назначение и цели создания системы

### 2.1. Вид автоматизируемой деятельности

Система предназначена для автоматизации сбора, хранения, анализа и визуализации данных об активности пользователей рабочих станций в корпоративной сети, а также для централизованного управления локальными endpoint-агентами, политиками мониторинга, командами блокировки рабочей станции и отчетностью по активности.

### 2.2. Объекты использования

- Организации с локальной сетью и парком рабочих станций Windows, Linux и macOS.
- Системные администраторы и специалисты информационной безопасности.
- Руководители подразделений, которым требуется анализ активности сотрудников.
- Аналитики и ответственные лица, формирующие отчеты по активности, инцидентам и нарушениям политик.

### 2.3. Цели создания системы

- Повысить прозрачность использования рабочих станций в организации.
- Обеспечить централизованное хранение событий активности и аномалий.
- Сократить время подготовки отчетов по пользователям, компьютерам, периодам и категориям активности.
- Обеспечить управление политиками локальных агентов из единой веб-панели.
- Реализовать устойчивую доставку событий при временных сбоях сети за счет локальной очереди агента и асинхронной серверной обработки.
- Снизить риски неконтролируемого использования ресурсов за счет обнаружения аномалий, уведомлений и команд управления агентом.

## 3. Характеристика объектов автоматизации

### 3.1. Краткие сведения об объекте автоматизации

Объект автоматизации представляет собой корпоративную информационную среду, включающую рабочие станции пользователей, серверную инфраструктуру и локальную сеть организации. На рабочих станциях устанавливается локальный агент мониторинга, который собирает технические события активности и передает их в серверную часть. Серверная часть построена на микросервисной архитектуре: каждый доменный сервис отвечает за отдельную область данных и имеет собственную базу PostgreSQL.

Система включает:

- локальный агент мониторинга `LocalEndpointAgent` на Python с Rust-модулем для низкоуровневых системных вызовов;
- серверные микросервисы ASP.NET Core/.NET: `ActivityService`, `AuthService`, `UserService`, `MetricsService`, `NotificationService`, `ReportService`, `AgentManagementService`;
- API Gateway, предоставляющий единую REST-точку входа для веб-панели;
- брокер сообщений RabbitMQ для асинхронной передачи событий между сервисами;
- раздельные базы данных PostgreSQL для доменных сервисов;
- веб-панель администратора на React с Material UI и Recharts.

### 3.2. Условия эксплуатации

- Сетевая инфраструктура: локальная сеть с пропускной способностью не менее 100 Мбит/с.
- Серверная часть: Linux-сервер или контейнерная среда Docker/Docker Compose.
- Рабочие станции: Windows, Linux или macOS с установленным агентом.
- Режим работы: постоянный фоновый сбор событий агентами и круглосуточная доступность серверной части.
- Кратковременные разрывы соединения допустимы; агент обязан сохранять события в локальной SQLite-очереди и отправлять их после восстановления связи.
- Пики нагрузки ожидаются в начале рабочего дня, при массовой синхронизации агентов, при построении отчетов и при обработке накопленных событий после восстановления сети.

## 4. Требования к системе

### 4.1. Требования к архитектуре и функционированию

#### 4.1.1. Архитектура системы

Система строится на микросервисной архитектуре. Веб-панель взаимодействует только с API Gateway по REST API. Gateway выполняет проверку JWT-токенов, авторизацию, аудит административных действий и маршрутизацию запросов к внутренним gRPC-сервисам.

Внутренняя серверная часть включает:

- `AuthService` - аутентификация, роли, сессии, JWT и refresh-токены;
- `UserService` - пользователи, компьютеры и связь «пользователь - компьютер»;
- `ActivityService` - прием событий активности, хранение, оценка риска и выявление аномалий;
- `MetricsService` - агрегация событий и расчет метрик;
- `NotificationService` - формирование и хранение уведомлений;
- `ReportService` - построение ежедневных, периодических и сводных отчетов, экспорт данных;
- `AgentManagementService` - регистрация агентов, heartbeat, политики, версии политик, команды и синхронизация;
- API Gateway - внешняя REST-точка входа и слой интеграции frontend с gRPC-сервисами.

Обмен событиями между сервисами осуществляется через RabbitMQ. Для надежной обработки используется подход outbox/inbox: сервис-источник сохраняет событие перед публикацией, а сервисы-получатели дедуплицируют обработанные сообщения.

#### 4.1.2. Протоколы взаимодействия

- Frontend - Gateway: REST API поверх HTTP/HTTPS.
- Gateway - внутренние сервисы: gRPC.
- LocalEndpointAgent - ActivityService/AgentManagementService: gRPC с транспортным токеном агента.
- Межсервисные события: RabbitMQ с MassTransit.
- Live-обновления веб-панели: SSE-канал Gateway.

Все внешние соединения в промышленной эксплуатации должны работать через TLS. Секреты подключения хранятся в переменных окружения и не включаются в систему контроля версий.

#### 4.1.3. Масштабируемость

Архитектура предусматривает горизонтальное масштабирование серверных сервисов и независимое масштабирование доменных баз данных. При увеличении числа рабочих станций добавляются новые экземпляры локального агента без изменения архитектуры серверной части. Асинхронная шина RabbitMQ снижает связность сервисов и позволяет обрабатывать события независимо в сервисах метрик, отчетов и уведомлений.

#### 4.1.4. Требования к пользователям системы

- Рабочие станции пользователей: до 50 на этапе внедрения.
- Администраторы системы: до 3 пользователей с правами управления агентами, политиками, пользователями и настройками.
- Аналитики и руководители: до 20 пользователей с доступом к отчетам и агрегированным показателям.
- Рядовые пользователи не взаимодействуют с агентом напрямую; агент работает в фоновом режиме.

#### 4.1.5. Показатели производительности и надежности

- Время отклика веб-интерфейса: не более 3 секунд при штатной нагрузке.
- Обработка событий активности: не менее 10 000 событий в час.
- Коэффициент готовности серверной части: не менее 0,99 в течение рабочего дня.
- Время восстановления после сбоя серверной части: не более 30 минут.
- События агента не должны теряться при временной недоступности сервера благодаря локальной SQLite-очереди.
- Системные сервисы должны предоставлять health-check endpoints для контроля состояния контейнеров.

### 4.2. Требования к функциям системы

#### 4.2.1. Локальный агент мониторинга

Локальный агент должен:

- собирать сведения о процессах и активных приложениях;
- фиксировать изменение активного окна;
- определять периоды активности и бездействия пользователя;
- собирать историю посещенных сайтов из локальных браузеров в рамках доступных прав;
- фиксировать сетевые соединения;
- отслеживать создание, изменение и удаление файлов в заданных пользовательских каталогах;
- собирать сведения об USB-устройствах;
- формировать inventory установленных приложений и процессов;
- фиксировать best-effort события пользовательской сессии: вход, выход, блокировка и разблокировка;
- отправлять события в `ActivityService` по gRPC;
- передавать heartbeat и техническое состояние в `AgentManagementService`;
- хранить очередь событий локально в SQLite при отсутствии связи;
- применять локально закешированные политики;
- выполнять команды управления, включая управляемую блокировку рабочей станции.

Агент не должен сохранять введенный пользователем текст, пароли и содержимое нажатий клавиш. Keylogging в составе Системы не реализуется.

#### 4.2.2. Сервис приема и обработки активности

`ActivityService` должен:

- принимать события активности от агентов по gRPC;
- валидировать структуру события, идентификатор пользователя, компьютера и агента;
- сохранять события в базе PostgreSQL;
- рассчитывать риск события на основании типа активности, времени, ресурса и заданных правил;
- выявлять аномалии и связывать их с исходными событиями;
- публиковать события `activity.created` и `activity.anomaly-detected` в RabbitMQ через outbox;
- предоставлять API для получения активности и проверки состояния сервиса.

#### 4.2.3. Сервис управления агентами

`AgentManagementService` должен:

- регистрировать агентов и хранить сведения об их версии, компьютере и статусе;
- принимать heartbeat с размером очереди, временем последнего сбора, временем последней отправки, ошибками, версией политики и capabilities агента;
- хранить политики агента, включая разрешенные и запрещенные приложения, браузеры, параметры мониторинга и настройки блокировки;
- вести историю версий политик и поддерживать восстановление предыдущей версии;
- создавать, выдавать и отслеживать команды агенту;
- обрабатывать статусы команд: pending, running, success, failed, timeout, deadletter;
- поддерживать синхронизацию политик и batch-операции.

#### 4.2.4. Сервисы метрик, отчетов и уведомлений

`MetricsService` должен потреблять события из RabbitMQ, рассчитывать агрегированные показатели по пользователям, компьютерам, периодам, категориям активности, аномалиям и нарушениям политик.

`ReportService` должен формировать ежедневные, недельные, месячные и произвольные отчеты, поддерживать фильтрацию по пользователям, компьютерам, подразделениям и диапазонам дат, а также экспортировать данные в CSV/XLSX.

`NotificationService` должен формировать уведомления о событиях и аномалиях, поддерживать каналы `in_app`, `email`, `webhook`, хранить статус прочтения и обеспечивать получение счетчика непрочитанных уведомлений.

#### 4.2.5. Сервис аутентификации и управления пользователями

`AuthService` должен обеспечивать регистрацию, вход, выход, выдачу JWT и refresh-токенов, хранение ролей и сессий.

`UserService` должен обеспечивать CRUD-операции с пользователями и компьютерами, а также поддерживать связь «пользователь - компьютер» по правилу 1:1.

#### 4.2.6. Веб-панель администратора

Веб-панель должна содержать следующие разделы:

- `Dashboard` - оперативные KPI, активность, аномалии, блокировки, live-обновления;
- `Agents` - список агентов, статусы, политики, версии политик, команды, rollout и rollback;
- `Users` - управление пользователями и привязанными компьютерами;
- `Reports` - отчеты, тренды, агрегаты, экспорт;
- `Analytics` - аналитика за день, неделю, месяц и произвольный период, фильтры и drill-down;
- `Settings` - общие, security, notification и monitoring-настройки, whitelist/blacklist и alert rules;
- `Login` - вход пользователя в систему.

Интерфейс должен поддерживать светлую и темную тему, адаптивные таблицы, графики и формы управления.

### 4.3. Требования к видам обеспечения

#### 4.3.1. Информационное обеспечение

Для хранения данных используются отдельные базы PostgreSQL:

- `activities` - события активности, аномалии и outbox;
- `auth` - пользователи аутентификации, роли и сессии;
- `users` - пользователи организации и компьютеры;
- `metrics` - агрегированные метрики;
- `notifications` - уведомления и inbox обработанных событий;
- `reports` - отчетные проекции, сводки и экспорт;
- `agents` - агенты, политики, версии политик, команды и синхронизация.

Обмен данными между frontend и Gateway выполняется в JSON-формате. Внутренние контракты сервисов описываются protobuf-файлами. Все текстовые данные должны храниться в кодировке UTF-8.

#### 4.3.2. Программное обеспечение

- Backend: ASP.NET Core/.NET, gRPC, Entity Framework Core, Npgsql.
- Асинхронные сообщения: RabbitMQ, MassTransit.
- Базы данных: PostgreSQL 16.
- Frontend: React 18, Material UI, Recharts, Axios, React Router.
- Локальный агент: Python 3, SQLite, gRPC, Rust/PyO3-модуль для системных функций.
- Наблюдаемость: OpenTelemetry, Prometheus, Grafana.
- Развертывание: Docker, Docker Compose, Nginx для frontend/HTTPS.

#### 4.3.3. Техническое обеспечение

Сервер: процессор не менее 4 ядер, оперативная память не менее 8 ГБ, SSD не менее 50 ГБ, сетевой интерфейс 100 Мбит/с или выше.

Рабочие станции: Windows 10/11, Linux или macOS, наличие прав для установки агента и предоставления необходимых системных разрешений.

Администраторские рабочие места: актуальные версии Google Chrome, Mozilla Firefox, Microsoft Edge или Safari.

#### 4.3.4. Организационное обеспечение

- Назначение администратора Системы.
- Определение перечня рабочих станций, пользователей и компьютеров.
- Подготовка политики мониторинга и допустимых источников данных.
- Настройка регламента резервного копирования.
- Определение порядка обновления серверной части и агентов.
- Подготовка инструкций для администраторов, аналитиков и рядовых пользователей.

### 4.4. Требования к безопасности

- Аутентификация пользователей выполняется по логину и паролю с безопасным хешированием паролей.
- Доступ к функциям ограничивается ролевой моделью.
- Для пользователей применяются роли: администратор, аналитик, руководитель, пользователь.
- Frontend взаимодействует с сервером через Gateway с использованием JWT.
- Агенты взаимодействуют с сервером по gRPC с транспортным токеном.
- Все внешние соединения в промышленной среде должны быть защищены TLS.
- Секреты приложения, пароли БД, ключи JWT, токены агентов и пароли RabbitMQ хранятся в переменных окружения.
- Все административные действия должны записываться в журнал аудита с указанием пользователя, времени, типа действия, ресурса и результата.
- Система не должна собирать содержимое переписки, вводимые пароли и полный текст пользовательского ввода.

### 4.5. Требования к эргономике

- Веб-интерфейс должен быть доступен в актуальных браузерах.
- Основные функции должны быть доступны через понятную навигацию: мониторинг, агенты, пользователи, отчеты, аналитика, настройки.
- Время освоения основных операций для пользователя с базовыми навыками ПК не должно превышать 30 минут.
- Отчеты должны представляться в виде таблиц, графиков и сводных показателей.
- Элементы управления политиками и командами агентов должны отображать результат операции и ошибки выполнения.

### 4.6. Требования к документированию

Должны быть подготовлены:

- описание архитектуры и схемы взаимодействия компонентов;
- описание баз данных и основных таблиц;
- описание gRPC/REST API и маршрутов Gateway;
- инструкция по установке и запуску через Docker Compose;
- инструкция по установке локального агента;
- руководство администратора;
- руководство аналитика;
- описание процедур резервного копирования и восстановления;
- сценарии модульного, интеграционного и функционального тестирования.

## 5. Состав и содержание работ

### 5.1. Этапы разработки

- Этап 1, 2 недели: проектирование архитектуры, выделение микросервисов, проектирование БД и контрактов protobuf.
- Этап 2, 2 недели: разработка серверных сервисов `ActivityService`, `AuthService`, `UserService`, `AgentManagementService`.
- Этап 3, 2 недели: реализация RabbitMQ-интеграции, outbox/inbox, сервисов метрик, отчетов и уведомлений.
- Этап 4, 1 неделя: разработка React-веб-панели, страниц Dashboard, Agents, Users, Reports, Analytics, Settings.

## 6. Порядок контроля и приемки

### 6.1. Виды испытаний

Модульное тестирование:

- проверка приема и сохранения событий активности;
- проверка оценки риска и выявления аномалий;
- проверка расчета метрик;
- проверка формирования отчетов и экспорта;
- проверка регистрации агентов, heartbeat, политик и команд;
- проверка авторизации и ролевого доступа;
- проверка основных экранов веб-панели.

Интеграционное тестирование:

- агент отправляет событие в `ActivityService`, событие сохраняется и появляется в отчетах;
- `ActivityService` публикует событие в RabbitMQ, а `MetricsService`, `ReportService`, `NotificationService` обновляют свои проекции;
- администратор меняет политику агента, агент получает новую версию политики и применяет ее;
- администратор отправляет команду блокировки, агент получает команду и возвращает статус выполнения;
- при разрыве соединения агент накапливает события локально, после восстановления связи отправляет очередь.

Функциональное тестирование:

- проверка входа пользователя и доступа к разделам по ролям;
- проверка CRUD пользователей и агентов;
- проверка фильтрации отчетов по датам, пользователям и компьютерам;
- проверка экспорта отчетов;
- проверка отображения live-данных;
- проверка ведения журнала административных действий;
- проверка производительности при обработке не менее 10 000 событий в час.

### 6.2. Критерии приемки

- Реализованы основные функции, указанные в разделе 4.2.
- Система запускается через Docker Compose.
- Веб-панель доступна и взаимодействует с Gateway.
- Gateway корректно взаимодействует с gRPC-сервисами.
- События активности сохраняются и участвуют в построении метрик и отчетов.
- Управление агентами, политиками и командами работает из веб-панели.
- Система стабильно работает в течение 24 часов без перезапуска.
- Подготовлена техническая и пользовательская документация.
